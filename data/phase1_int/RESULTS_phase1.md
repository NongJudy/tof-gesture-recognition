# ผลการทดลอง Phase 1 — การตรวจสอบเวลาด้วย logic analyzer

เอกสารฉบับสมบูรณ์ · ปรับปรุง 10 ก.ย. 2026
ตัวเลขทุกค่าในเอกสารนี้คำนวณด้วยวิธีเดียวกัน คือการปรับเส้นตรงกับขอบทุกอัน

## 1. เหตุผลที่ต้องทำ Phase 1

PROJECT_FACTS TRAP หมายเลข 12 ระบุว่าทั้งโหมด 8x8 และ 4x4 วัดอัตราเฟรมได้
เร็วกว่าที่ระบุในดาต้าชีทราว 0.7 เปอร์เซ็นต์ เท่ากันทั้งสองโหมด
เป็นค่าคงที่เชิงระบบ ไม่ใช่สัญญาณรบกวน ผู้ต้องสงสัยมีสองราย

1. วงจร RC ในเซ็นเซอร์เดินเร็วกว่าที่ควร
2. นาฬิกาบนบอร์ด NUCLEO เพี้ยน ทำให้ตัวเลขที่วัดได้ทั้งหมดผิด

ปัญหาคือมีนาฬิกาเพียงสองตัวที่ขัดแย้งกัน จึงไม่มีทางตัดสินว่าใครผิด
ต้องหานาฬิกาตัวที่สามที่เป็นอิสระมาช่วยตัดสิน

ถ้าข้อ 2 เป็นจริง ตัวเลขทั้ง 8 แถวใน timing matrix ของ Phase 0 จะใช้ไม่ได้ทั้งหมด
Phase 1 จึงเป็นเงื่อนไขที่ต้องผ่านก่อนจะเชื่อผลใด ๆ จาก Phase 0

## 2. อุปกรณ์และวิธี

### 2.1 เครื่องมือ

logic analyzer แบบใช้ชิป Cypress FX2LP
VID:PID 0925:3881 ระบบรายงานชื่อว่า Saleae Logic
8 ช่องสัญญาณ ใช้คริสตัล 24 MHz เป็นฐานเวลา

ซอฟต์แวร์ sigrok-cli และ PulseView รุ่น nightly จาก sigrok.org
ไดรเวอร์ WinUSB ติดตั้งผ่าน Zadig

### 2.2 การต่อสาย

ใช้ขั้วต่อ Morpho เพราะบอร์ดขยาย X-NUCLEO-53L8A1 เสียบทับขั้วต่อ Arduino ไว้

| ช่อง | สัญญาณ | ขา MCU | ตำแหน่ง |
|---|---|---|---|
| CH0 | SCL | PB8 | CN10 ขา 3 |
| CH1 | SDA | PB9 | CN10 ขา 5 |
| CH2 | INT | PA4 | CN7 ขา 32 |
| GND | — | — | CN10 ขา 9 |

ขั้วต่อ Morpho ของบอร์ด Nucleo-64 ไม่มีตัวหนังสือกำกับชื่อขา
จึงต้องยืนยันตำแหน่งด้วยการวัด ไม่ใช่การนับหรือการอ่าน

การยืนยันทำสี่ชั้น

1. มัลติมิเตอร์โหมดเสียงร้อง ยืนยันว่าเข็มบน Morpho ต่อถึงรูบนขั้วต่อ Arduino
   ที่มีตัวหนังสือกำกับ คือ SCL/D15 SDA/D14 และ A2
2. วัดแรงดันเฉลี่ยที่ปลายสาย ได้ 2.7 2.7 และ 3.3 โวลต์
   ยืนยันว่าเป็นสัญญาณ 3.3 โวลต์ ไม่ใช่ขาไฟเลี้ยง 5 โวลต์
3. รูปสัญญาณบนจอต่างกันตามที่ทำนายไว้ล่วงหน้า
4. PulseView ถอดรหัส I2C ได้ที่อยู่ 0x29 ซึ่งเท่ากับ 0x52 เมื่อรวมบิตอ่านเขียน
   ตรงกับที่ PROJECT_FACTS หัวข้อ 1.3 บันทึกไว้

### 2.3 คำสั่งที่ใช้ ทำซ้ำได้

เก็บข้อมูลคาบเฟรม

    sigrok-cli -d fx2lafw --config samplerate=1m --samples 10000000 \
               -O binary -o <ชื่อไฟล์>.bin

เก็บข้อมูลบัส

    sigrok-cli -d fx2lafw --config samplerate=12m --samples 12000000 \
               -O binary -o <ชื่อไฟล์>.bin

วิเคราะห์

    python pc_tools/analyze_calib.py <ไฟล์...> --channel 2 --expected 60.0 --edge falling
    python pc_tools/analyze_bus.py <ไฟล์...>

### 2.4 วิธีคำนวณคาบ

ตำแหน่งขอบสัญญาณลำดับที่ i ควรอยู่ที่ a บวก b คูณ i โดย b คือคาบเฉลี่ย
หาค่า b ด้วยวิธีกำลังสองน้อยสุดจากขอบทุกอัน

วิธีนี้ถูกเลือกหลังจากพบว่าวิธีเดิม ซึ่งใช้เพียงขอบแรกกับขอบสุดท้าย
ให้ความไม่แน่นอนสูงกว่าประมาณสิบเท่า
เหตุผลคือขอบแต่ละอันมีความสั่นของตัวเอง วัดได้ราว 200 ไมโครวินาทีในโหมด 4x4
เมื่อใช้เพียงสองจุด ความสั่นของทั้งสองจุดจะปรากฏเต็มที่ในผลลัพธ์
ส่วนการปรับเส้นตรงใช้ทุกจุด ความสั่นแบบสุ่มจึงหักล้างกัน

การจำลอง 2000 ครั้งยืนยันว่าความไม่แน่นอนลดจาก 46 ppm เหลือ 4.5 ppm

## 3. การสอบเทียบนาฬิกา

### 3.1 หลักการ

ก่อนใช้ logic analyzer ตัดสินว่าเซ็นเซอร์หรือบอร์ดผิด
ต้องรู้ก่อนว่าตัว logic analyzer เองแม่นแค่ไหน

จึงให้บอร์ดปล่อยคลื่นสี่เหลี่ยมที่คำนวณค่าได้แน่นอน แล้วให้ logic analyzer วัด

คลื่นสร้างด้วย TIM3 ช่อง 3 ออกทางขา PC8 ซึ่งเป็นขาที่บอร์ดขยายไม่ได้ใช้
เขียนรีจิสเตอร์โดยตรงเพราะโปรเจคปิดโมดูล TIM ของ HAL ไว้
ค่าที่ตั้ง PSC เท่ากับ 0 และ ARR เท่ากับ 41999 ได้ 1000.000000 Hz พอดี ไม่มีเศษ

### 3.2 การทดสอบเชิงลบ

ทดสอบความถี่ห้าค่า เพื่อพิสูจน์ว่าโปรแกรมคำนวณความคลาดจริง
ไม่ได้พิมพ์ศูนย์ทิ้งไว้

| ตั้ง (Hz) | PSC | ARR | ได้จริง (Hz) | คลาด (ppb) |
|---|---|---|---|---|
| 100 | 6 | 59999 | 100.000000 | 0 |
| 1000 | 0 | 41999 | 1000.000000 | 0 |
| 10000 | 0 | 4199 | 10000.000000 | 0 |
| 60000 | 0 | 699 | 60000.000000 | 0 |
| 60 | 10 | 63635 | 60.000342 | 5714 |

ค่า 60 Hz สร้างเป๊ะไม่ได้ เพราะ 84e6 หารด้วย 120 เท่ากับ 700000
ซึ่งเกินขีดของตัวนับ 16 บิต จึงต้องใส่ตัวหารช่วยแล้วหารไม่ลงตัว
การที่รอบนี้ให้ค่าไม่เป็นศูนย์ ยืนยันว่าโปรแกรมคำนวณจริง
เลขศูนย์ในรอบอื่นจึงมีความหมาย

### 3.3 ผลการสอบเทียบ

| รอบ | ความถี่ที่วัดได้ (Hz) | คลาด (ppm) |
|---|---|---|
| 1 | 999.905082 | -94.918 |
| 2 | 999.904390 | -95.610 |
| 3 | 999.904302 | -95.698 |
| เฉลี่ย | 999.904592 | **-95.408** |
| SD | 0.000349 | 0.349 |

ความไม่แน่นอนของแต่ละรอบ บวกลบ 0.001 ppm
duty cycle 50.000 เปอร์เซ็นต์ทั้งสามรอบ ยืนยันว่าโหมด toggle ทำงานถูกต้อง

**ข้อสรุป** นาฬิกาบอร์ดกับนาฬิกา logic analyzer ตรงกันภายใน 95 ppm
ห่างจากค่าที่ต้องแยกให้ออก คือ 7000 ppm ถึง 73 เท่า
คริสตัลสองตัวที่ไม่เกี่ยวข้องกัน โอกาสที่จะเพี้ยนพร้อมกันด้วยขนาดเท่ากันพอดี
แทบเป็นศูนย์ จึงสรุปได้ว่าทั้งคู่ถูกต้อง และใช้ logic analyzer เป็นตัวตัดสินได้

## 5. ผลตามสมมติฐาน

### H1 และ H2 ใครเดินเร็ว และ DWT เชื่อถือได้หรือไม่

ทำการทดลองแบบสลับโหมด A แล้ว B แล้ว A เพื่อแยกดริฟต์ออกจากความต่างระหว่างโหมด

| ชุด | โหมด | เวลา | ppm เทียบสเปก | SD | n |
|---|---|---|---|---|---|
| A1 | 4x4 | 12:13 | 6890.4 | 16.94 | 3 |
| B | 8x8 | 12:16 | 7582.4 | 13.83 | 3 |
| A2b | 4x4 | ~12:30 | 6844.3 | 1.68 | 3 |

ประมาณค่า 4x4 ณ เวลาที่วัด B โดยแทรกเชิงเส้นตามเวลา ได้ 6882.2 ppm

**ความต่างระหว่างโหมด 700.2 ppm ความคลาดมาตรฐาน 11.3 t เท่ากับ 61.7**

ทั้งสองโหมดเร็วกว่าสเปก 6800 ถึง 7600 ppm
วัดด้วยเครื่องมือที่สอบเทียบกับนาฬิกาบอร์ดแล้ว ตรงกันภายใน 95 ppm
คริสตัลคลาดได้อย่างมาก 50 ppm จึงเป็นไปไม่ได้ที่จะทำให้เกิด 7600 ppm

**ข้อสรุป H1** เซ็นเซอร์คือตัวที่เดินเร็ว ไม่ใช่นาฬิกาบอร์ด

**ข้อสรุป H2** DWT บนบอร์ดวัดถูกต้อง ยืนยันสามทางอิสระ
คือคลื่นสอบเทียบ 95 ppm คาบเฟรมอยู่ในช่วงที่บอร์ดวัดเอง
และความถี่ SCL ห่างจากค่าที่ตั้ง 132 ppm
ดังนั้น timing matrix ทั้ง 8 แถวจาก Phase 0 เชื่อถือได้

การที่สองโหมดเร็วไม่เท่ากันยิ่งสนับสนุนข้อสรุป
เพราะถ้าเป็นความผิดของนาฬิกาบอร์ด ทั้งสองโหมดต้องเพี้ยนเท่ากันเป๊ะ

อัตราส่วนคาบ 8x8 ต่อ 4x4 เท่ากับ 3.99722 ต่างจาก 4 พอดี -0.0695 เปอร์เซ็นต์
แสดงว่าโมเดล tick ใน TRAP หมายเลข 15 เป็นค่าประมาณ ไม่ใช่กลไกที่แม่นยำ

### H3 บัสว่างกี่เปอร์เซ็นต์

| โหมด | บัสทำงาน | บัสว่าง | SD | ทำนายไว้ |
|---|---|---|---|---|
| 4x4 | 27.197 % | **72.803 %** | 0.124 | 72 % |
| 8x8 | 20.107 % | **79.893 %** | 0.319 | 80 % |

คำทำนายถูกทั้งสองโหมด

เป็นหลักฐานตรงชิ้นแรกว่าคอขวดอยู่ที่เซ็นเซอร์ ไม่ใช่ที่ MCU หรือที่บัส
เดิมมีแต่หลักฐานทางอ้อมจากความสัมพันธ์ระหว่างการหน่วงกับคาบ

### H4 สัญญาณนาฬิกา SCL วิ่งจริงกี่กิโลเฮิรตซ์

| โหมด | วัดได้ | แก้ตามสอบเทียบ | ต่างจาก 400.000 |
|---|---|---|---|
| 4x4 | 399.9090 kHz | 399.947 kHz | -132 ppm |
| 8x8 | 399.9272 kHz | 399.965 kHz | -87 ppm |

ความละเอียด 2.4 ppm จากการวัดข้ามพัลส์ 78000 ถึง 107000 ตัว

คำทำนายเดิมว่าน่าจะต่ำกว่า 400 เพราะการปัดเศษ ผิด
เหตุผลที่ลงตัวคือ PCLK1 เท่ากับ 42 MHz โหมด fast duty 2
คาบเท่ากับ 3 คูณ CCR คูณ Tpclk1 ทำให้ CCR เท่ากับ 35 พอดี เป็นจำนวนเต็ม

**ข้อสรุป** ไม่ต้องแก้ตัวเลข 400 kHz ที่ใช้ในเอกสาร

หมายเหตุ การวัดทีละพัลส์ให้ค่า 400.00 kHz พอดีทุกไฟล์ ส่วนเบี่ยงเบนศูนย์
ซึ่งเป็นผลจากความละเอียดไม่พอ ไม่ใช่ความแม่น
ที่ 12 MHz คาบ SCL เท่ากับ 30 ตัวอย่างพอดี แยกได้หยาบสุดบวกลบ 3.3 เปอร์เซ็นต์

### H5 ระยะจาก INT ถึงจังหวะเริ่มการคุย

| โหมด | INT ถึง START | SD | เทียบ INT ถึงพัลส์ SCL แรก |
|---|---|---|---|
| 4x4 | **6.61 us** | 0.039 | 9.17 us |
| 8x8 | **6.64 us** | 0.039 | 9.19 us |

ทำนายไว้ต่ำกว่า 50 ไมโครวินาที ผลจริงเร็วกว่าที่คาดราว 7 เท่า

นิยามที่ใช้คือระยะจากขอบขาลงของ INT ถึงจังหวะ START บนบัส I2C
ซึ่งคือจุดที่ SDA เปลี่ยนจากสูงเป็นต่ำขณะที่ SCL ยังสูง

เดิมวัดถึงพัลส์ขาขึ้นแรกของ SCL ซึ่งเกิดหลัง START ราวหนึ่งคาบนาฬิกา
ทำให้ค่ายาวเกินจริงราว 39 เปอร์เซ็นต์
พบความคลาดนี้จากการเทียบผลของสคริปต์กับการวางเคอร์เซอร์ในโปรแกรม

**ข้อสรุป** MCU ตอบสนองเร็วกว่าคาบเฟรมราว 2500 เท่า
ตอบ TRAP หมายเลข 15 ด้วยหลักฐานเชิงเวลาว่า INT ไม่ใช่คอขวด

## 6. สิ่งที่พบเพิ่มเติม ไม่ได้อยู่ในแผนเดิม

### 6.1 อัตราเฟรมของเซ็นเซอร์ไม่เสถียร

วัดโหมด 4x4 ด้วยอัตราสุ่มเดียวกันต่างเวลากัน

| เวลา | ppm เทียบ 60 Hz |
|---|---|
| ~10:58 | 6038.4 |
| ~11:45 | 6945.9 |
| ~11:55 | 6911.1 |
| 12:13 | 6890.4 |
| ~12:30 | 6844.3 |

พุ่งขึ้น 908 ppm ในชั่วโมงแรก แล้วค่อย ๆ ลดลงราว 102 ppm ในชั่วโมงถัดมา
โหมด 8x8 แสดงรูปแบบเดียวกัน ลดลง 122 ppm ในช่วงเดียวกัน

การทดสอบดริฟต์ระหว่าง A1 กับ A2b ห่างกัน 17 นาที ได้ 46.1 ppm t เท่ากับ 4.69
ซึ่งมีนัยสำคัญ

หมายเหตุสำคัญ ด้วยตัวประมาณเดิม การทดสอบเดียวกันได้ t เท่ากับ 1.50
และเคยสรุปว่าไม่มีดริฟต์ ซึ่งผิด
ความละเอียดของเครื่องมือไม่พอทำให้สรุปผิด ตรวจไม่พบไม่เท่ากับไม่มี

**สาเหตุยังพิสูจน์ไม่ได้** ผู้ต้องสงสัยหลักคืออุณหภูมิ
เพราะเซ็นเซอร์ใช้ RC oscillator ซึ่งมีค่าสัมประสิทธิ์อุณหภูมิสูง
และรูปแบบพุ่งขึ้นแล้วเข้าที่สอดคล้องกับการอุ่นเครื่องจนถึงสมดุลความร้อน
แต่ยังไม่ได้วัดอุณหภูมิ จึงยังสรุปไม่ได้

ไม่พบเอกสารใดใน project knowledge ที่รายงานความไม่เสถียรนี้

100.3 ถึง 100.4 ไมโครวินาที เท่ากันทั้งสองโหมด
ทั้งที่คาบเฟรมต่างกันสี่เท่า และเวลาอ่านข้อมูลต่างกันสามเท่า
เป็นค่าคงที่ของฮาร์ดแวร์เซ็นเซอร์

สังเกตว่าเซ็นเซอร์ปล่อย INT กลับสูงหลังจาก 100 ไมโครวินาที
ในขณะที่การอ่านข้อมูลใช้เวลา 4512 ไมโครวินาที
แปลว่าเซ็นเซอร์ไม่ได้รอให้ MCU อ่านเสร็จก่อนปล่อยสัญญาณ

### 6.4 ความสั่นของขอบ INT

| โหมด | ความสั่น | สัดส่วนของคาบ |
|---|---|---|
| 4x4 | ราว 200 us | 1.2 % |
| 8x8 | ราว 100 us | 0.15 % |

ความสั่นเท่ากันทั้งขอบขาขึ้นและขอบขาลง ต่างกันไม่ถึง 0.05 ตัวอย่าง
แสดงว่าความกว้างพัลส์คงที่ ความสั่นอยู่ที่จังหวะที่เซ็นเซอร์ยิง

### 6.5 พบข้อบกพร่องในโค้ดของโปรเจค

ไฟล์ my_tof.c บรรทัด 284

    m_skip += (m_stream_delta - 1U);

สมมติว่า delta มากกว่า 1 หมายถึงมีเฟรมหาย ซึ่งผิดสำหรับโหมด 8x8

ที่โหมด 8x8 ค่า delta เท่ากับ 4 คงที่ทุกเฟรม เป็นเรื่องปกติ
เพราะ streamcount ของเซ็นเซอร์เพิ่มขึ้นตามการวัดภายใน ไม่ใช่ตามเฟรมที่ส่งออก
ทำให้ค่า skip เพิ่มขึ้นทีละ 3 ทุกเฟรมโดยไม่มีอะไรผิดจริง

ยืนยันจากข้อมูล delta เท่ากับ 4 เป๊ะทุกเฟรมไม่แกว่งเลย
ถ้าเป็นเฟรมหายจริงต้องแกว่งไม่แน่นอน

## 7. ข้อจำกัดของงานนี้

1. การทดลอง A-B-A ใช้ n เท่ากับ 3 ต่อชุด
   การทดสอบดริฟต์จึงมีอำนาจต่ำ ควรเพิ่มเป็น 5 รอบต่อชุด

2. วัดชุด B เพียงจุดเดียว ไม่ทราบว่าตัว B เองนิ่งหรือไม่
   ควรทำเป็น A B A B A

3. การประมาณค่า 4x4 ณ เวลาที่วัด B ใช้การแทรกเชิงเส้น
   ซึ่งเป็นสมมติฐาน ทั้งที่ทราบแล้วว่าดริฟต์ไม่เป็นเส้นตรง
   บรรเทาได้เพราะช่วงเวลาสั้นเพียง 17 นาที และความต่างระหว่างโหมด
   ใหญ่กว่าดริฟต์ในช่วงนั้นราว 15 เท่า

4. ยังไม่ได้พิสูจน์ว่าความคลาดของ logic analyzer ไม่ขึ้นกับความถี่
   สอบเทียบทำที่ 1 kHz แต่นำผลไปใช้กับ 60 Hz และ 15 Hz
   ในเชิงฟิสิกส์ไม่มีกลไกที่ทำให้เพี้ยนตามความถี่ เพราะเครื่องนับ tick ของตัวเอง
   แต่ยังไม่ได้วัดยืนยัน

5. ยังไม่ทราบสาเหตุที่สองโหมดเร็วไม่เท่ากัน

6. ยังไม่ทราบสาเหตุของดริฟต์ ยังไม่ได้วัดอุณหภูมิ

7. การวัดสัดส่วนบัสว่าง นับจากขอบ SCL แรกถึงขอบสุดท้ายของแต่ละชุด
   ไม่รวมช่วง START และ STOP ซึ่งไม่มีพัลส์นาฬิกา
   ค่าที่แท้จริงจึงสูงกว่าเล็กน้อย ราวหนึ่งคาบนาฬิกาต่อชุด

## 10. สรุปสำหรับผู้อ่านที่มีเวลาน้อย

ปัญหาที่ค้างมาตั้งแต่ Phase 0 คือไม่ทราบว่าอัตราเฟรมที่วัดได้เร็วเกินสเปก
เพราะเซ็นเซอร์เดินเร็ว หรือเพราะนาฬิกาบอร์ดเพี้ยน

งานนี้ตอบว่า **เซ็นเซอร์คือตัวที่เดินเร็ว** โดยใช้ logic analyzer
ที่สอบเทียบกับนาฬิกาบอร์ดแล้วพบว่าตรงกันภายใน 95 ppm
ซึ่งเล็กกว่าความคลาดที่ต้องอธิบายถึง 73 เท่า

ผลข้างเคียงคือ timing matrix ทั้ง 8 แถวจาก Phase 0 เชื่อถือได้
และได้ตัวเลขใหม่ที่ไม่เคยมีมาก่อน ได้แก่ สัดส่วนบัสว่าง เวลาตอบสนองของ INT
และความไม่เสถียรของอัตราเฟรมตามเวลา
