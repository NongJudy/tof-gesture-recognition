ข้อมูลวัดคาบเฟรมเซ็นเซอร์ VL53L8CX ด้วย logic analyzer
เก็บวันที่ 10 ก.ย. 2026

=== เงื่อนไข ===
บอร์ด NUCLEO-F411RE (MB1136 rev C) + X-NUCLEO-53L8A1
firmware switches:
  MY_CAL_ENABLE      = 0   (ปิดคลื่นสอบเทียบ)
  MY_TOF_USE_INT     = 1
  MY_TOF_TIMING_MODE = 1
  MY_TOF_FAST_READ   = 1   (แถว D/H ใน timing matrix)
  MY_TOF_DELAY_US    = 0
  MY_TOF_USE_4X4     = 1 สำหรับ int4x4_*, 0 สำหรับ int8x8_*
นาฬิกา HSE 84 MHz (CLK,84000000 ยืนยันจาก UART)

=== สายวัด ===
CH0 -> CN10 ขา 3  (PB8, SCL)
CH1 -> CN10 ขา 5  (PB9, SDA)
CH2 -> CN7  ขา 32 (PA4, INT)   <- ช่องที่ใช้วิเคราะห์
GND -> CN10 ขา 9

ยืนยันตำแหน่งขา 4 ชั้น:
  1. มัลติมิเตอร์เสียงร้อง ต่อถึงรู Arduino ที่มีตัวหนังสือ
     (SCL/D15, SDA/D14, A2)
  2. แรงดันเฉลี่ย 2.7 / 2.7 / 3.3 V  ไม่ใช่ 5V
  3. รูปสัญญาณต่างกันตามที่ทำนาย
  4. PulseView ถอดรหัส I2C ได้ address 0x29 = 0x52 ตรงกับ FACTS

=== คำสั่งที่ใช้เก็บ (ทำซ้ำได้) ===
sigrok-cli -d fx2lafw --config samplerate=1m --samples 10000000
           -O binary -o int<mode>_run<N>.bin

=== คำสั่งวิเคราะห์ ===
python pc_tools/analyze_calib.py int4x4_run1.bin int4x4_run2.bin
       int4x4_run3.bin --channel 2 --expected 60.0 --edge falling
python pc_tools/analyze_calib.py int8x8_run1.bin int8x8_run2.bin
       int8x8_run3.bin --channel 2 --expected 15.0 --edge falling

=== ข้อสรุป ===
1. TRAP #12 ตอบได้แล้ว: เซ็นเซอร์คือตัวที่เร็ว ไม่ใช่นาฬิกาบอร์ด
   ทั้งสองโหมดเร็วเกินสเปก 6000-7800 ppm
   วัดด้วย logic analyzer ที่สอบเทียบกับนาฬิกาบอร์ดแล้ว ตรงกันใน 95 ppm
   คริสตัลคลาดได้แค่ 50 ppm จึงเป็นไปไม่ได้ที่จะทำให้เกิด 7800 ppm

2. สองโหมดเร็วไม่เท่ากัน (+0.612% กับ +0.780% ต่างกัน 1678 ppm)
   ขัดกับที่ FACTS เดิมบันทึกว่าเท่ากัน 0.7%
   การไม่เท่ากันยิ่งตัดความเป็นไปได้ว่านาฬิกาบอร์ดผิด
   เพราะถ้าบอร์ดผิด ทั้งสองโหมดต้องเพี้ยนเท่ากันเป๊ะ
   สาเหตุยังไม่ทราบ [ยังไม่ได้ตรวจ]

3. 8x8 ไม่ใช่ 4 เท่าของ 4x4 พอดี
   อัตราส่วนคาบ = 3.99334 ต่างจาก 4 เท่ากับ -0.1665%
   โมเดล tick ใน TRAP #15 เป็นค่าประมาณ ไม่ใช่กลไกจริง

4. พัลส์ INT กว้าง 100 us เท่ากันทั้งสองโหมด
   ทั้งที่คาบต่างกัน 4 เท่า เป็นค่าคงที่ของฮาร์ดแวร์เซ็นเซอร์
   ไม่พบใน paper ใดใน project knowledge

5. ความสั่นของคาบต่างกันมาก
   4x4 SD 325 us = 1.96% ของคาบ
   8x8 SD 149 us = 0.23% ของคาบ
   สาเหตุยังไม่ทราบ [ยังไม่ได้ตรวจ]

=== พบข้อบกพร่องในโค้ดเรา ===
my_tof.c:284  m_skip += (m_stream_delta - 1U)
สมมติว่า delta>1 คือเฟรมหาย ซึ่งผิดที่โหมด 8x8
ที่ 8x8 delta=4 คงที่ทุกเฟรม เป็นเรื่องปกติ ไม่ใช่เฟรมหาย
ทำให้ skip เพิ่มทีละ 3 ทุกเฟรมโดยไม่มีอะไรผิดจริง
ต้องแก้ก่อนรายงานผล ยังไม่แก้ตอนนี้เพราะจะเปลี่ยนเงื่อนไขกลางการทดลอง

=== การทดลองควบคุม C-1 ===
เทียบค่าจาก UART ตอนไม่ต่อสายวัด กับตอนต่อสาย 4 เส้น
  rd_us     4512-4513  ->  4512-4513   ไม่เปลี่ยน
  rd_calls  1          ->  1
  rd_bytes  196        ->  196
  delta     1          ->  1
  dup       0          ->  0
สรุป: การจิ้มสายวัดไม่รบกวนบัส I2C ในระดับที่วัดได้
      (DWT ที่ 84 MHz ละเอียด 12 ns)

=== ข้อจำกัด ===
- ยังไม่ได้พิสูจน์ว่าความคลาดของ logic analyzer ไม่ขึ้นกับความถี่
  สอบเทียบทำที่ 1 kHz เท่านั้น แต่นำผลไปใช้กับ 60 Hz และ 15 Hz
  เชิงฟิสิกส์ไม่มีกลไกที่ทำให้เพี้ยนตามความถี่ แต่ยังไม่ได้วัดยืนยัน
- ยังไม่ทราบสาเหตุที่สองโหมดเร็วไม่เท่ากัน
- ยังไม่ทราบสาเหตุของความสั่น
